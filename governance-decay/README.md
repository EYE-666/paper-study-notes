一句话概括：

**Agent 原本能够遵守的上下文安全规则，可能在 Context Compaction 中被遗漏或移除，使其在面对相同违规请求时，更容易生成原本被禁止的操作。**

# 与信息利用能力下降的不同

Context Rot 可以概括为长上下文中的信息利用能力退化：**某段信息仍位于上下文中，模型却可能无法正确使用它。**

需要注意，**这两种机制在真实系统中可以同时发生**

# 数学模型和问题定义

## Agent 组成

**Agent Model：M**

负责根据当前上下文作出决策的 LLM。

**History：H**

Agent 在执行任务过程中积累的消息历史，包括指令、回复和工具返回。

**Agent Harness**

运行模型、维护历史、控制工具交互和上下文管理的外部框架。

**Compaction Operator：C**

Harness 中负责压缩上下文的操作。论文的设定是：用压缩后的替代内容替换历史中较早的一段，而不是必须把全部历史都变成一个摘要。

**Governance Constraint：p**

约束 Agent 行为的规则，例如“不得向公司域名之外的收件人发送邮件”。它可能来自用户提供的组织政策、检索到的组织记忆，或工具加载的政策文档。

本文重点研究的是**通过上下文承载、没有被框架保证永久保留的规则**

## Context Compaction的数学表示

论文设定一个上下文预算 ***B***。

当历史 Token 数量超过预算时：

```math
\operatorname{tokens}(H)>B
```

Harness 执行压缩操作，用压缩后的内容替换较早的一段历史。论文用下面的记号表示请求到来前的历史经过压缩：

```math
C(H_{\lt t})
```

```math
H_{\lt t}=[p,m_1,m_2,\ldots,m_{100}]
```

若被压缩部分覆盖了这些消息，压缩后的历史可以简化示意为：

```math
C(H_{\lt t})=[s]
```

问题在于：压缩前的历史包含约束 ***p***，压缩后的内容却不一定仍然表达这个约束。

直观上可以写成：

```math
p\in H_{\lt t},\qquad p\notin C(H_{\lt t})
```

但这里的集合成员记号只是简写。**规则是否存活，应看摘要是否保留原规则的语义，而不是原句是否逐字出现。**

论文在实验中把这种语义保留称为 **constraint survival**，并使用 LLM judge 评估

## Governance Decay 的核心公式

论文给出的定义是：

```math
\Delta_{\text{decay}}=v\left(M,[C(H_{\lt t});r]\right)-v\left(M,[H_{\lt t};r]\right)
```

其中：

***v(M,H)***：模型 ***M*** 在上下文 ***H*** 下产生违反 ***p*** 的行为的概率。

因此，这个量测量的是：**面对同一违规请求，压缩历史后相对于保留完整历史，违规概率增加了多少。**

## 攻击目的

攻击目标是使合法约束 ***p*** 从压缩后的历史中消失，或者不再被准确表达，**进而提高后续违规请求被执行的概率**。

```math
p\notin C(H)
```

同时要区分：

- **被动 Governance Decay**：没有攻击者介入，普通压缩也可能遗漏规则。

- **Compaction-Eviction Attack**：攻击者主动利用或诱导压缩过程，使规则更容易丢失。

论文研究的是：**Agent 的安全规则存放在会参与压缩的对话历史、记忆或工具加载内容中时，可能被 Context Compaction 删除；它并没有证明被框架专门保护、不会参与压缩的 System / Developer Instructions 也会以同样方式丢失。**

# Threat Model：攻击者能控制什么？

## 受保护对象与信任边界

需要保护的是合法的 Governance Constraint ***p***，使它在任务推进与上下文压缩后仍然约束 Agent。

攻击者控制的是 **Agent 会摄入的上下文数据**，例如工具返回值、检索文档。攻击者不能直接修改模型 ***M***、***System Prompt*** 或 Compaction Operator ***C***。

## 两种攻击途径

1. **Volume**：注入大量看起来正常的内容，促使压缩触发或挤占摘要预算。

2. **Summarizer Injection**：在待处理内容中加入面向摘要器的指令，诱导它在总结时省略合法约束。

# ConstraintRot benchmark

## 一个测试场景如何构成？

每个场景是一段 Agent 会话，包含三个部分：

1. **Policy Turn**：先给出约束 ***p***。

2. **Benign Task Turns**：加入较长的正常任务交互，增长上下文。

3. **Trigger Request**：最后给出一个自然完成方式会违反 ***p*** 的请求。

## Soft和Hard任务

- **Soft organizational policies**：特定组织规定的限制，动作本身可能很正常，例如采购、发邮件、选择部署区域。模型通常不能仅凭预训练知识知道这家组织的具体要求。

- **Hard safety norms**：模型可能已经倾向于拒绝的动作，例如泄露隐私、读取秘密或破坏生产环境。即使上下文规则丢失，它也可能继续拒绝。

## 两个指标

### **Violation rate：Agent 最终是否产生违规动作？**

解析最终工具调用及参数，确定是否存在被禁止的效果，例如收件人的域名是否在允许范围外。这个主指标使用确定性判定，**不依赖 LLM judge**。

### **Constraint survival：压缩结果是否仍表达原规则？**

这是语义判定，论文使用独立 LLM judge，并以关键词启发式及三裁判多数投票交叉检查。

**实验中的工具调用只被解析，不会真正执行。** 所谓违规，指生成了按规则判定为违规的动作，不代表真实发生邮件外发、数据库删除或秘密泄露

# 实验结果

## 主结果：压缩后违规率显著上升，但模型之间不一致

## Soft / Hard 差异

- Soft policies：0% → 50%，增加约 50 个百分点。

- Hard norms：0% → 6%，增加约 6 个百分点。

**解释：组织特定规则更依赖上下文承载；模型已有的安全倾向可能掩盖 hard norms 的规则丢失。**

# 机制分析与消融

## 约束是否存活，与违规率高度相关

## 消融一：是长度问题，还是删除规则的问题？

**逻辑是：保持规则可见的长上下文没有导致违规；较短但没有规则的摘要却导致大量违规；把规则补回又恢复为 0%。** 因此，在这组测试中，单纯“上下文太长”不足以解释现象，规则的删除与恢复具有直接作用。

## 消融二：是 Summarizer，还是后续 Agent？

把摘要器模型与决策模型交叉组合，可区分“谁写了摘要”与“谁依据摘要行动”的影响。

关键例子：**GLM 自己做摘要时在七模型主实验中表现很好，但作为 Agent 读取 DeepSeek 写出的摘要时，违规率达到 53%。** 因而，主实验中 GLM 的低违规不能单独归因于它作为决策模型“绝不会违规”。

**更严谨的理解：摘要器是否保留规则，是重要的上游影响因素；后续 Agent 的行为差异也仍然存在。**

## 压缩强度：摘要越短，风险总体越高

论文扫描的 summary budget 为 **15、30、50、80、150、300 words**。

从 300 words 收紧到 15 words 时：

- 汇总 constraint survival：88% → 23%。

- 汇总 violation：7% → 28%。

# Compaction-Eviction Attack

## Volume：用大量内容影响压缩

攻击者提供大量看起来正常的材料，使较早的规则更容易失去位置。

## Summarizer Injection：攻击负责总结历史的部分

攻击内容不是只要求 Agent 直接做违规动作，而是诱导摘要器删掉合法约束。例如，伪称某条合规规则已经过时，要求压缩时忽略。

**解释：攻击者先改变后续决策所能看到的信息，再让 Agent 面对违规请求。** 即使后续 Agent 没有看到原始恶意指令，它仍可能因为看不到合法限制而执行请求。

## 固定攻击与搜索后的攻击的不同

**固定攻击**：用预先确定的一段诱导内容测试模型。

**搜索后的攻击**：尝试多种表述策略，再为各模型选择表现最强的策略。

本文搜索六种策略：

1. 将规则描述为已经废弃。

2. 将规则描述为与当前任务无关。

3. 以 Token Budget 为理由要求省略规则。

4. 直接写给摘要器的提示。

5. 冒充 System 的摘要指令。

6. 冒充 Operator 权威。

**“对固定攻击 Prompt 的鲁棒性，不等于对经过搜索的攻击策略具有鲁棒性”**

# Constraint Pinning

## 核心思想

既然问题之一是规则在压缩时被删除，就把规则从有损压缩对象中单独保护出来。

论文提出由 Harness：

1. 把治理约束提取到 **pinned buffer**。

2. 让这个 buffer 不参与有损压缩。

3. 每次压缩后把规则**逐字重新注入**上下文。

4. 在每一步做 **integrity check**，要求压缩后的上下文仍然蕴含被固定的规则

# 压力测试：Constraint Pinning 是否彻底解决了问题？

**没有。它在本文主实验中有效，但在近期上下文的权威冒充攻击下仍会失败。**

## 为什么规则明明还在，也会违规？

最初的失败路径是：

**规则被压缩掉 → Agent 决策时看不到规则。**

Pinning 修补了这一点，但近期攻击可以制造另一个问题：

**规则仍然在 → 攻击内容冒充有权限更新政策的 Operator → 模型把伪造的新声明当成可以覆盖旧规则的指令。**

# 贡献和结论

## 主要贡献

四项贡献：

1. 提出 **ConstraintRot benchmark**，用确定性动作判定衡量规则失效。

2. 系统测量 **Governance Decay**，并研究模型、压缩方式与规则保留之间的关系。

3. 提出 **Compaction-Eviction Attack**，展示摄入数据可以诱导压缩删除合法规则。

4. 提出 **Constraint Pinning**，并报告其效果、开销及失效边界。

## 结论

**这篇论文最值得记住的是：治理规则不仅需要在某一轮被遵守，还需要在 Harness 改写上下文后继续存在；而让规则继续存在之后，还必须区分谁有权修改它。**
